# ZMG0004 — IKJCT441 for REXX (design draft)

Status: draft for the board, nothing built yet. Question 3 is decided;
question 4 waits for a measurement.

## Goal

ISPF on MVS 3.8j knows no REXX. It reaches the variables of the dialog that
called it only through the variable access routine `IKJCT441`, which Greg
Price's usermod `ZP60038` (rework 2019-07-27) added to TSO. That `IKJCT441`
serves CLIST variables only: when the top element of the TSO input stack is
not a CLIST (`INSEXEC`), it ends with return code 40.

`ZMG0004` replaces `IKJCT441` with a version that also serves the variables of
a running REXX exec, so `ADDRESS ISPEXEC` with `VGET`, `VPUT`, `DISPLAY` and
the panel variables works from REXX. It serves any REXX implementation that
follows the TSO/E contract below — BREXX/370 and REKX/370 alike — and changes
nothing for CLISTs.

## Starting point

- The source of `ZP60038` is public domain and ships inside its job stream
  (`IKJCT441`, about 1,350 bytes, RENT, linked into the LPA module `IKJPTGT`
  as an alias). It calls `IKJINIT` in `IKJCT433`, added by `ZP60014`.
- `ZMG0004` is a `++USERMOD` against `EBB1102` with `++MOD(IKJCT441)` and
  `PRE(ZP60038)` (which itself requires `ZP60014` and `UY01301`). The link
  edit statements for `IKJPTGT` already name `IKJCT441` (from `ZP60038`'s
  `SGIKJ441` update), so no JCLIN is needed. A CLPA activates it; `RESTORE`
  returns to the `ZP60038` level.
- Both TSO usermods in this register (`ZMG0001`, `ZMG0002`) change EXEC;
  `ZMG0004` does not touch EXEC.

## The contract with a REXX implementation

`IKJCT441` uses only what TSO/E defines, and nothing product specific:

1. `ECTENVBK` (ECT + X'30') points to the ENVBLOCK of the active REXX
   environment, or is zero. ENVBLOCK + X'130' holds the top input stack
   element at the start of the running exec (question 3 below).
2. The ENVBLOCK starts with `ENVBLOCK`; `ENVBLOCK_IRXEXTE` points to the
   external entry point vector; its `IRXEXCOM` entry holds the address of a
   routine with the calling sequence and semantics of TSO/E `IRXEXCOM`
   (parameter list, SHVBLOCK, `SHVRET` flags, return codes).
3. `IKJCT441` calls that address directly. It never loads or links a module
   by an `IRX*` name; that namespace belongs to REKX/370.

The call, as `IKJCT441` makes it (offsets in hex):

| Item | Value |
|---|---|
| R1 | -> parameter list of four entries, the high bit set in the fourth |
| Parameter 1 | -> the 8-byte string `IRXEXCOM` (a value, not a module name) |
| Parameters 2 and 3 | -> a fullword of zero |
| Parameter 4 | -> the SHVBLOCK, IBM's 32-byte layout below |
| R0 | -> ENVBLOCK |
| R15 on return | negative: the call failed; otherwise the flags are in `SHVRET` |

| Offset | Field | `S` (update) | `N` (fetch next) |
|---|---|---|---|
| +00 | `SHVNEXT` | 0 | 0 |
| +04 | `SHVUSER` | 0 | in: length of the name buffer (252) |
| +08 | `SHVCODE` | `S` | `N` |
| +09 | `SHVRET` | out: flags | out: flags (`SHVLVAR` at the end, `SHVTRUNC` if a buffer is too short) |
| +0A | reserved | 0 | 0 |
| +0C | `SHVBUFL` | 0 | in: length of the value buffer (32,767) |
| +10 | `SHVNAMA` | -> name | -> name buffer |
| +14 | `SHVNAML` | name length | out: length of the name returned |
| +18 | `SHVVALA` | -> value | -> value buffer |
| +1C | `SHVVALL` | value length | out: length of the value returned |

This is IBM's layout and meaning (TSO/E REXX Reference, IRXEXCOM).
BREXX/370's `maclib/SHVCB.mac` matches it. rekx370's `include/irx.h`
defines a 40-byte `struct shvblock` with two extra words and `shvnaml` as a
buffer length; an implementation that follows that header does not match
this call.

A REXX implementation sets `ECTENVBK` while its exec runs and restores the
previous value at the end, only if `ECTENVBK` still points to its own block
(the discipline of REKX/370's `IRXTERM`).

## Where the change goes

At `REDRIVE`, before `TM INSCODE,INSEXEC`:

```
REDRIVE  L     R7,ECT@
         ICM   R1,15,ECTENVBK-ECT(R7)   REXX environment active?
         BZ    CLIST                    no: the ZP60038 path, unchanged
         validate ENVBLOCK id, IRXEXTE, IRXEXCOM entry
         decide REXX or CLIST (open question 1)
         B     REXXPATH
CLIST    L     R6,ECTIOWA ...           unchanged from ZP60038
```

`REXXPATH` translates each request of the request list into one SHVBLOCK
call:

| Entry code | Meaning | SHVBLOCK |
|---|---|---|
| 1 `TSVERETR` | retrieve, create if undefined | `F`; on `SHVNEWV` a `S` with the caller's value (or null), then `F` again |
| 2 `TSVEUPDT` | update, create if undefined | `S` |
| 18 `TSVNOIMP` | retrieve, no create | `F`; `SHVNEWV` gives RC 52 |
| 3 `TSVELOC` | locate all, with token | `N`; `SHVLVAR` gives RC 20; token 0 starts a new sequence |

Return codes keep `ZP60038`'s values: `SHVBADN` and lengths out of range 36,
an unusable environment or an `IRXEXCOM` failure 40, an undefined variable 52.
Codes 4, 8, 12 and 16 (rescan, evaluation, label, system variable) have no
REXX meaning and are not returned on the REXX path.

## Findings and open questions

Sources: the `IKJECT` mapping of MVS 3.8j (mvslovers/maclib370), IBM z/OS
TSO/E Programming Services, chapter "Using the variable access routine
IKJCT441" (SA32-0973), and the `ZP60038` source.

1. **`ECTENVBK` on MVS 3.8j — settled by the mapping.** The 3.8j `IKJECT`
   ends with three reserved words at X'2C', X'30' and X'34'; the ECT is X'38'
   bytes long. X'30' is inside the ECT and reserved, and z/OS gave that word
   the name `ECTENVBK`. `ECTUSER` (X'20', "reserved for installation use") is
   a different word and stays untouched. Still to measure: that no local
   modification on TK5 or MVS/CE writes X'30' in a TSO session (BREXX/370's
   `test/ectenvbk.rexx` checks it, but in batch it passes trivially).
2. **Variable names — settled by IBM.** REXX variables are accessed "using
   the REXX direct interface", with no symbol substitution and no case
   translation; an uninitialised variable returns a null value, not its
   name; a stem can be retrieved with `TSVNOIMP` and not set, compound names
   such as `A.1` can be set. `ZMG0004` therefore uses the direct requests
   `F`, `S` and `N` and passes names unchanged.
3. **REXX or CLIST, when both are active — open.** IBM states that REXX execs
   and CLISTs cannot access each other's variables, but not how IKJCT441
   chooses. The cases:

   | Chain | Must serve | "CLIST on top of the input stack wins" |
   |---|---|---|
   | REXX → ISPF | REXX | right (no CLIST element) |
   | REXX → CLIST → ISPF | CLIST | right (the CLIST pushed its element) |
   | CLIST → REXX → ISPF | REXX | **wrong**: the calling CLIST's element is still on top, because a REXX exec pushes none |

   So `IKJCT441` needs to know whether the top input stack element was
   pushed before or after the REXX exec started.

   **Decided (board, 2026-11-03): the REXX side records the top input
   stack element (`IOSTELM`) when its exec starts, in a field of the
   contract, and `IKJCT441` serves REXX while that element is still on top.**
   The alternative, a REXX element of its own on the input stack, was
   rejected: the stack is TSO's input source (GETLINE and PUTGET read from
   its top, errors and attention flush it, other modules inspect its top
   element), so an element without input behind it would change what
   commands called from REXX read, and TSO/E does not do it either.

   **The field: ENVBLOCK + X'130' (+304), the first of the four words TSO/E
   leaves reserved at the end of the 320-byte ENVBLOCK.** It holds the top
   input stack element (`IOSTELM`) at the start of the exec that is running
   now; zero means no exec is running. A nested exec in the same environment
   saves the word when it starts and writes it back when it ends. The other
   three reserved words stay reserved.
   Why there: both implementations keep the ENVBLOCK in IBM's layout (REKX/370
   with version `0042` instead of `0100`, same layout), and `IKJCT441` reaches
   the word directly from `ECTENVBK`. Rejected: a word in the work block
   extension (REKX/370 points `ENVBLOCK_WORKBLOK_EXT` at an internal block of
   its own, not at IBM's layout), `ENVBLOCK_USERFIELD` (belongs to users and
   exits), a slot in IRXEXTE (a vector of entry points), and a reserved word
   of the ECT (it belongs to the session, not to the REXX environment).
   Risk, to be measured later: when TSO flushes the input stack (an error or
   an attention) while an exec runs, the recorded element can disappear;
   `IKJCT441` then compares against an element that is gone and takes the
   CLIST path.
4. **Who owns a retrieved value — open.** IBM documents only that VALUEPTR
   "contains the address of the value", not how long it stays valid. On the
   CLIST path it points into the CLIST's value table. `IRXEXCOM` copies into a
   caller buffer, and `IKJCT441` frees its work area on return, so the REXX
   path needs a buffer that outlives the call and an anchor to free it later
   (on the next call, or when the environment ends). `IKJCT441` is reentrant
   in the PLPA and has no anchor of its own. Candidates: a work area the REXX
   implementation provides through the contract (it then owns the lifetime),
   or a subpool 78 buffer anchored in a word both sides agree on.
   **Board, 2026-11-03: measure first.** (1) Time and storage of a full
   `N` sweep for an exec with large stems (for example 10,000 entries).
   (2) Whether ISPF takes over name and value at once, so that a buffer
   living until the next call is enough. Until then the buffer stays
   internal to the REXX routine, with no contract field.
   Two more measurements belong here: (3) whether ISPF ever leaves a
   `TSVELOC` sequence before RC=20 (each sequence holds a 33 KB subpool 1
   block until RC=20 frees it), and (4) whether ISPF issues `TSVEUPDT`
   inside a `TSVELOC` sequence; with IRXEXCOM, a request other than `N`
   may restart the `N` sequence (check the TSO/E REXX Reference), and
   `IKJCT441` would not notice.

## How ISPF calls IKJCT441

From ISPF's author (2020): at every `ISPEXEC` call from a CLIST, ISPF 2.0
retrieves all variables with `TSVELOC`, and it writes each updated ISPF
variable back with `TSVEUPDT`. It uses neither `TSVERETR` nor `TSVNOIMP`.
So the REXX path that matters is `TSVELOC` (SHVBLOCK `N`) and `TSVEUPDT`
(`S`), and every `ISPEXEC` call sweeps every variable of the exec,
compound variables included.

Measured under ISPF V2R2M0 on TK5 (`zmg0004/test/ispf`):

- ISPF does not take over a value when `TSVELOC` returns it. `ISPMSERV` records
  the value address and length per variable and copies the values after RC=20.
  So name and value must stay valid beyond RC=20; `IKJCT441` keeps them in
  chunks chained from ENVBLOCK+X'134' and frees those when the next sequence
  starts. This word is proposed, not decided.
- The table holds 2,048 variables without a check. 2,100 short names in a CLIST
  abend the process with the unchanged `ZP60038` module as well.
- ISPF skips names longer than 8 characters by itself, and they do not count
  against the table. So only the limit of 2,048 and names with a period need
  handling on the REXX path; a length filter is not needed for safety.

## Tests (own container, TK5 and MVS/CE)

- CLIST regression first: an ISPF CLIST dialog and a test driver that calls
  `IKJCT441` with each entry code give the same results before and after
  `ZMG0004`.
- REXX path with a test driver: set, retrieve, retrieve/no-create, locate all,
  against a REXX environment that implements the contract.
- Nesting: REXX calls CLIST calls ISPF, and CLIST calls REXX calls ISPF.
- `RESTORE` of `ZMG0004` brings back the `ZP60038` module.

## Not in this usermod

The `IRXEXCOM` routine on the REXX side (BREXX/370: planned for 3.1.0, on a
feature branch; REKX/370 has its own), and any change to ISPF.
